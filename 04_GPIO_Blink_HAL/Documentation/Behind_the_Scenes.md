# 🔬 Behind the Scenes — STM32 HAL GPIO

> This document explains what happens behind the simple two-line LED blink program.

The LED blink program looks very simple:

```c
while (1)
{
    HAL_GPIO_TogglePin(MY_LED_GPIO_Port, MY_LED_Pin);
    HAL_Delay(500);
}
```

But behind these two lines, STM32 performs several initialization and hardware-level operations.

This document explores what happens **before and during the execution of this code**.

---

# 1. 🧩 The Basic Program

The application logic is:

```c
while (1)
{
    HAL_GPIO_TogglePin(MY_LED_GPIO_Port, MY_LED_Pin);
    HAL_Delay(500);
}
```

At first glance, this looks very simple.

But before the `while(1)` loop starts, STM32CubeIDE-generated code performs several initialization steps.

The basic execution flow is:

```text
HAL_Init()
    ↓
SystemClock_Config()
    ↓
MX_GPIO_Init()
    ↓
while(1)
    ↓
HAL_GPIO_TogglePin()
    ↓
HAL_Delay()
    ↓
Repeat
```

---

# 2. ⚙️ What Happens Before `while(1)`?

The generated `main.c` contains initialization code similar to:

```c
int main(void)
{
    HAL_Init();

    SystemClock_Config();

    MX_GPIO_Init();

    while (1)
    {
        HAL_GPIO_TogglePin(MY_LED_GPIO_Port, MY_LED_Pin);
        HAL_Delay(500);
    }
}
```

The three important initialization functions are:

```c
HAL_Init();
SystemClock_Config();
MX_GPIO_Init();
```

Each one has a different purpose.

---

# 3. 🏗️ `HAL_Init()`

The first initialization function is:

```c
HAL_Init();
```

This initializes the STM32 HAL environment required by the application.

The HAL provides a common API for interacting with STM32 peripherals.

For example:

```c
HAL_GPIO_TogglePin();
HAL_GPIO_WritePin();
HAL_GPIO_ReadPin();
HAL_Delay();
```

Instead of directly manipulating hardware registers everywhere in the application, we can use these higher-level HAL functions.

---

# 4. ⏱️ `SystemClock_Config()`

The next important function is:

```c
SystemClock_Config();
```

A microcontroller requires a clock to operate.

The system clock provides the timing reference used by the MCU and its peripherals.

Conceptually:

```text
Clock Source
     ↓
Clock Configuration
     ↓
System Clock
     ↓
CPU + Peripherals
```

The exact clock configuration depends on the STM32 device and the configuration selected in STM32CubeMX.

---

# 5. 🕒 Why Do Peripherals Need a Clock?

STM32 peripherals are clocked modules.

Before using a peripheral, its corresponding clock generally needs to be enabled.

For example, if we want to use GPIOA, the GPIOA peripheral clock needs to be enabled.

STM32 provides the **RCC — Reset and Clock Control** peripheral for managing peripheral clocks and reset functions.

For GPIOA, Cube-generated code can contain a statement similar to:

```c
__HAL_RCC_GPIOA_CLK_ENABLE();
```

Conceptually:

```text
RCC
 ↓
Enable GPIOA Clock
 ↓
GPIOA becomes clocked
 ↓
GPIOA can be configured and used
```

---

# 6. 🧠 RCC — Reset and Clock Control

RCC stands for:

**Reset and Clock Control**

The RCC peripheral is responsible for important clock and reset management functions within the STM32.

For this GPIO project, one important operation is enabling the GPIO peripheral clock.

For example:

```c
__HAL_RCC_GPIOA_CLK_ENABLE();
```

This tells the microcontroller to enable the clock for GPIOA.

Without enabling the required peripheral clock, the GPIO peripheral cannot be configured and used normally.

---

# 7. 🔌 GPIO Initialization

After the system clock configuration, the generated code calls:

```c
MX_GPIO_Init();
```

This function contains the GPIO configuration generated by STM32CubeMX.

Conceptually:

```text
MX_GPIO_Init()
       ↓
Enable GPIO clock
       ↓
Configure GPIO parameters
       ↓
Initialize GPIO
```

For our project, PA5 is configured as an output.

---

# 8. 🏷️ PA5 → `MY_LED`

The onboard user LED of the NUCLEO-F401RE is connected to:

```text
LD2
 ↓
Arduino D13
 ↓
STM32 PA5
```

In STM32CubeMX, PA5 was configured as:

```text
GPIO_Output
```

and assigned the user label:

```text
MY_LED
```

CubeMX then generates definitions similar to:

```c
#define MY_LED_Pin GPIO_PIN_5
#define MY_LED_GPIO_Port GPIOA
```

Therefore:

```text
MY_LED_GPIO_Port → GPIOA
MY_LED_Pin       → GPIO_PIN_5
```

---

# 9. 🧱 GPIO Configuration Structure

During initialization, HAL uses a GPIO configuration structure.

A simplified representation is:

```c
GPIO_InitTypeDef GPIO_InitStruct = {0};
```

The structure contains configuration parameters for the GPIO pin.

For example:

```c
GPIO_InitStruct.Pin = MY_LED_Pin;
GPIO_InitStruct.Mode = GPIO_MODE_OUTPUT_PP;
GPIO_InitStruct.Pull = GPIO_NOPULL;
GPIO_InitStruct.Speed = GPIO_SPEED_FREQ_LOW;
```

The important parameters are:

| Parameter | Meaning |
|---|---|
| `Pin` | Selects the GPIO pin |
| `Mode` | Defines input/output/alternate-function behavior |
| `Pull` | Configures pull-up/pull-down behavior |
| `Speed` | Configures GPIO output speed |

---

# 10. 📌 Pin Configuration

For this project:

```c
GPIO_InitStruct.Pin = MY_LED_Pin;
```

Since:

```c
#define MY_LED_Pin GPIO_PIN_5
```

the selected pin is:

```text
GPIO_PIN_5
```

which corresponds to:

```text
PA5
```

---

# 11. 📤 GPIO Output Mode

The LED pin is configured as an output:

```c
GPIO_InitStruct.Mode = GPIO_MODE_OUTPUT_PP;
```

Here:

```text
GPIO_MODE_OUTPUT_PP
```

means:

**GPIO Output Push-Pull**

This allows the MCU to actively drive the GPIO output.

Conceptually:

```text
PA5
 │
 ├── HIGH
 │
 └── LOW
```

The output state can therefore be changed by the application.

---

# 12. 🔗 Pull-Up / Pull-Down

The configuration also contains:

```c
GPIO_InitStruct.Pull = GPIO_NOPULL;
```

This means no internal pull-up or pull-down resistor is being configured for this GPIO.

Conceptually:

```text
Pull-Up
    ↓
GPIO pulled toward HIGH

Pull-Down
    ↓
GPIO pulled toward LOW

No Pull
    ↓
No internal pull resistor
```

For this LED output configuration:

```c
GPIO_NOPULL
```

is used.

---

# 13. ⚡ GPIO Speed

The generated configuration may contain:

```c
GPIO_InitStruct.Speed = GPIO_SPEED_FREQ_LOW;
```

GPIO speed controls the output switching characteristics of the GPIO.

For a simple LED blink application, high GPIO speed is not required.

Therefore:

```c
GPIO_SPEED_FREQ_LOW
```

is sufficient for this project.

The GPIO speed setting is different from the LED's visible blink frequency.

---

# 14. 🔧 Applying the GPIO Configuration

After filling the structure, HAL applies the configuration using:

```c
HAL_GPIO_Init(MY_LED_GPIO_Port, &GPIO_InitStruct);
```

Because:

```c
MY_LED_GPIO_Port
```

represents:

```c
GPIOA
```

the operation effectively configures GPIOA pin 5.

Conceptually:

```text
GPIO_InitTypeDef
       ↓
Configuration parameters
       ↓
HAL_GPIO_Init()
       ↓
GPIOA / PA5 configured
```

---

# 15. 🔁 What Happens Inside `HAL_GPIO_TogglePin()`?

The application calls:

```c
HAL_GPIO_TogglePin(MY_LED_GPIO_Port, MY_LED_Pin);
```

Which represents:

```c
HAL_GPIO_TogglePin(GPIOA, GPIO_PIN_5);
```

The HAL function operates on the GPIO hardware registers.

Conceptually:

```text
Application
     ↓
HAL_GPIO_TogglePin()
     ↓
GPIO HAL Driver
     ↓
GPIO Registers
     ↓
GPIOA
     ↓
PA5
     ↓
LD2
```

---

# 16. 🧠 GPIO Registers

At the hardware level, the STM32 GPIO peripheral contains registers used for configuration and data operations.

Some important GPIO registers include:

```text
MODER
OTYPER
OSPEEDR
PUPDR
IDR
ODR
BSRR
AFR
```

For example:

### MODER

Controls the GPIO mode.

```text
Input
Output
Alternate Function
Analog
```

### OTYPER

Controls the output type.

```text
Push-Pull
Open-Drain
```

### OSPEEDR

Controls GPIO output speed.

### PUPDR

Controls pull-up/pull-down configuration.

### IDR

Input Data Register.

Used to read GPIO input state.

### ODR

Output Data Register.

Contains GPIO output state information.

### BSRR

Bit Set/Reset Register.

Provides an efficient way to set or reset GPIO output bits.

# 17. 🔍 HAL vs Lower-Level Code

One of the important concepts behind this project is the abstraction provided by HAL.

The application calls:

```c
HAL_GPIO_TogglePin();
```

The HAL implementation then performs lower-level hardware operations.

Conceptually:

```text
Application Code
       ↓
HAL
       ↓
CMSIS / Device Definitions
       ↓
STM32 Registers
       ↓
Hardware
```

This creates different levels of abstraction.

---

# 18. 🏗️ Three Programming Levels

STM32 GPIO programming can be understood at different abstraction levels.

## Level 1 — HAL

Example:

```c
HAL_GPIO_TogglePin(GPIOA, GPIO_PIN_5);
```

### Advantages

- Easy to read
- Portable across STM32 devices within supported HAL families
- Faster development
- Easier peripheral configuration

---

## Level 2 — Lower-Level / CMSIS

CMSIS provides device-level definitions and structures that allow access to MCU registers.

Conceptually:

```text
CMSIS
 ↓
Peripheral structures
 ↓
Hardware registers
```

This provides more control than high-level HAL APIs.

---

## Level 3 — Direct Register Access

At the lowest level, the programmer can directly manipulate peripheral registers.

For example, GPIO registers can be accessed through the MCU's memory-mapped peripheral addresses.

This gives very fine control but makes the code more hardware-specific and generally less readable.

# 20. ✍️ `HAL_GPIO_WritePin()`

The HAL GPIO write function has the form:

```c
HAL_GPIO_WritePin(GPIO_TypeDef *GPIOx,
                 uint16_t GPIO_Pin,
                 GPIO_PinState PinState);
```

It requires:

```text
GPIO Port
+
GPIO Pin
+
Pin State
```

For example:

```c
HAL_GPIO_WritePin(GPIOA,
                  GPIO_PIN_5,
                  GPIO_PIN_SET);
```

Conceptually:

```text
GPIOA
  +
Pin 5
  +
SET
```

This changes the output state of the selected GPIO.

Instead of manually setting the output HIGH and LOW, we can toggle it.

Toggle means:

```text
HIGH → LOW
LOW  → HIGH
```

Repeatedly calling the function creates:

```text

 ↓

 ↓
ON
 ↓
OFF
 ↓
...
```

# 27. 🆚 HAL vs Bare-Metal

The same GPIO functionality can be implemented at different abstraction levels.

### HAL

```c
HAL_GPIO_TogglePin(GPIOA, GPIO_PIN_5);
```

### Lower Level

The programmer can work directly with GPIO registers.

Conceptually:

```text
HAL
 ↓
CMSIS / Register Definitions
 ↓
GPIO Registers
 ↓
Hardware
```

### Trade-Off

| Approach | Abstraction | Readability | Control |
|---|---:|---:|---:|
| HAL | High | High | Medium |
| CMSIS / LL | Medium | Medium | High |
| Direct Registers | Low | Lower | Very High |

The appropriate approach depends on the project requirements.

# 📌 Key Takeaways

```text
1. STM32 peripherals require clocking.
2. RCC controls peripheral clocks and reset functions.
3. GPIO must be configured before it can be used.
4. CubeMX generates the initialization code.
5. HAL provides high-level APIs for peripherals.
6. HAL functions eventually interact with hardware registers.
7. GPIO registers control the actual hardware behavior.
8. User labels make generated code easier to understand.
9. Reading HAL source code helps understand what happens underneath the API.
10. The same abstraction concept applies to UART, SPI, I2C, ADC, TIMERS, CAN, etc.
```
